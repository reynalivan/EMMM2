## 1. System Paradigm

EMMM2's backend is a **Modular Monolith** using **Strict Vertical Slices**.

- **No Horizontal Layers:** We do not use global `services/`, `repo/`, or `domain/` folders. Everything is grouped by business capability (features).
- **Strict Encapsulation:** Internal module layers (`domain`, `application`, `adapters`) are explicitly marked as `pub(crate)` in `mod.rs`.
- **The API Boundary:** Modules can **only** communicate with each other or expose functions to integration tests via their explicit `api.rs` facade. Never bypass `api.rs`.
- **Tauri Segregation:** Tauri IPC endpoints live exclusively inside `adapters/tauri/`. Core business logic (`application/`) must never import or depend on `tauri`.
- **Atomic Operations:** Direct filesystem manipulation by the frontend is forbidden. All disk writes and structural changes must go through the single app-managed `MutationCoordinator`. It owns the shared `OperationLock`, persistent operation journal, and active task registry; production command state must never manage or inject a second `OperationLock`.

## 2. Core Topology

- `src/modules/` -> The 16 Vertical Slices (The heart of the application).
- `src/platform/` -> Cross-cutting infrastructure (Filesystem wrappers, OS-level recycle bin, OperationLocks).
- `src/pipeline/` -> Complex orchestrators that span across multiple modules (e.g., Collection Apply Pipeline).
- `src/shared/` -> Global primitives, error definitions, and synchronous types.

## 3. Module Index (The 16 Slices)

1. **`automation`**: Owns global hotkeys, preset/Safe Mode actions and KeyViewer generation.
2. **`browser`**: Internal web browser integration and scraping logic.
3. **`catalog`**: Master DB logic, object tracking, and metadata taxonomy.
4. **`collections`**: Loadout snapshots and preset management (diffing applied states).
5. **`dashboard`**: Analytics, application telemetry, and overview statistics.
6. **`duplicates`**: Deep-scanning engine for finding redundant files across mod folders (Epic 9).
7. **`games`**: Game configuration management, executable paths, and registry logic.
8. **`ingestion`**: Import queue, background ZIP/RAR extraction, and drop-zone handling (Epic 5).
9. **`library`**: Disk-direct views of mod folders, basic mod manipulation, and read-only Mod Health analysis.
10. **`matching`**: Deep/Fuzzy matching engine bridging local folders to Master DB taxonomy (Epic 4).
11. **`mutation`**: The engine room. Houses the `MutationCoordinator`, operation journaling, and recovery systems.
12. **`reconciliation`**: Disk-to-DB syncing. Runs silently to fix discrepancies and handles 'Safe Mode' transitions (Epic 7).
13. **`settings`**: App-level configuration and global preferences.
14. **`system`**: Bootstrap routines, logging, themes, application lifecycle, and the shared game process/focus detector used by runtime hotkeys and KeyViewer maintenance.
15. **`updates`**: Upstream update checkers for both the app and installed mods.
16. **`workspace`**: The active mod routing, file watcher lifecycle, and live grid logic.

One worker per game coalesces pending commits, yields to foreground intent, backs off transient failures, and parks missing watcher/config coverage until an explicit wake. Journal, checkpoint, receipt, snapshot, and projected event carry persistent physical root identity; foreign-root work is preserved for repair, never published or rolled back as a new-root operation. Trusted batches lexically align configured roots, journal endpoints and rename events in the Windows verbatim namespace before validation/scanning; historical source paths are never filesystem-canonicalized, and physical folder spelling is preserved. Required snapshot/capture barriers are stricter than normal leaf switching.
- **Projection proof and repair:** Rename healing selects exact source rows and descendants, verifies each destination's native identity, and updates object rows by verified ID; normalized spelling is not ownership. Checkpoints cannot cross a same-epoch `NeedsRepair` revision. Coherent collection/Safe Mode barriers validate repair evidence even with no pending commit; repair closure follows completed successor lineage. Snapshots expose a repair reason so frontend waiters stop rather than poll forever, while retaining verified disk state. Unproven legacy rows require reconciliation, not guessed identity.
- **Projection failure scope:** Proven toggle scopes stay scoped when reconciliation fails; a database or unavailable-source error does not trigger a second full scan. Full discovery is selected only when scope proof is absent. Rename-confirmation ambiguity isolates overlapping operation roots, then retries independent work while the repair-hole checkpoint clamp remains intact. An existing replacement identity is terminal ownership repair; a temporarily unavailable target remains retryable. Projection/runtime diagnostics correlate game, epoch, disk/publication revision, scope mode and worker wait/elapsed time without adding another queue.
- **Watcher rename lineage:** Expected edges are registered before storage changes but cannot suppress events until committed disk proof exists. Early echoes defer; abort, expiry, overflow, or foreign identity restores dirty/repair evidence. Historical child endpoints follow committed successor and ancestor renames within the same session. A verified reconcile watermark prunes only fully consumed dependency groups, not unseen debouncer backlog. Missing native edges remain a conservative repair condition.
- **Immutable transaction admission:** Collection capture/apply/restore/recovery, conflict fix/trash, Safe Mode/preset, randomizer and structural import/move/delete/rename share a four-running-or-queued-operations-per-game RAII limit. Excess immutable transactions reject explicitly before waiting on storage locks. Normal latest-desired toggles are outside this limit. Metadata-only operations do not acquire snapshot barriers. Writer proofs validate both the originally captured root location and its configured physical identity after waiting; source proofs must not rebind a replacement folder.

- **File System Watcher and Authority:** The activation coordinator exclusively owns the active `notify-rs` watcher; React has no start/stop command. A watcher feeds scoped Disk Reconcile batches, then queues runtime publication only after commit and release of the game/operation leases. Inactive games keep a live watcher and bounded event receiver; activation takes over that same watcher, session, and receiver so buffered debounce events are not dropped. A changed Mods root identity or missing coverage rejects takeover and requires a new watcher plus full catch-up. In-memory authority tokens bind root identity, watcher session, reconcile revision, and dirty evidence; a clean revisit reuses the last projection, dirty roots receive scoped catch-up, and identity/gap/settings ambiguity forces one full scan. Ambiguous single-path renames request a full reconcile; rejected watcher results retry from current dirty authority with bounded backoff instead of waiting indefinitely for another event. Focus/Mods-view checks can return a no-change cached revision only while the operation lock is free, the journal has no pending disk commit for that game, watcher repair has no dropped event, and the authority proof still matches; otherwise normal reconcile runs. A completed core index retains repair-preflight eligibility after a later unavailable watcher result. Snapshot-sensitive writers require the latest applied projection and clean authority; direct prefix toggles with original ancestry proof may proceed through ordinary dirt or projection lag; root/ancestor replacement and coverage gaps still reject. Other transactions retain scoped/full repair. Internal preflight and terminal mutation reconcile record the watcher proof under the same game/operation lease as their disk projection, retrying one full pass if watcher continuity changes. Applied projection with unproven watcher continuity carries an `AuthorityPending` warning rather than being treated as a failed disk projection; an unaccepted toggle proof keeps its journal pending for retry. Tokens are deliberately not persisted across restart.
- **Game Activation:** `settings::set_active_game` is the single activation owner. It increments a monotonic generation, persists the selection, hands watcher coverage from the previous game to the target without an uncovered interval, publishes `game_activation:status`, and returns while baseline/catch-up work continues. Stale generations cannot publish readiness or runtime work. Onboarding completes the first game's core index with watcher continuity before activation; a clean handoff reuses the matching applied revision without a second scan. Initial and recovered activation both require an applied current watcher revision with no pending disk commit or suppressor repair. A clean revision behind a pending commit stays pending and is rechecked on a bounded timer under a nonblocking operation lease without scanning again or delaying foreground mutations; dropped watcher events require a full repair scan. Source-unavailable results still publish their diagnostic status. Startup may install pre-activation coverage for its saved selected game; ordinary inactive prewarm cannot. Clearing the durable pending-onboarding marker follows readiness asynchronously and remains recoverable after restart. Later snapshot workers stay parked until that activation reports an applied revision, then index in the background. Inactive games are prewarmed sequentially.
- **Regional Workspace Toggle:** Identity-preserving mod, parent-activation, bulk-mod, and object-batch toggles hold the per-game lease, derive and identity-validate their complete scope, and journal every rename. Healthy known leaf scopes skip projection preflight; target/ancestor uncertainty retains scoped/full repair. Watcher dirt arriving during journal preparation receives one authoritative repair under the same game/operation guards, without replanning or rebinding targets; unresolved proof aborts the unapplied journal. Original identity, binding, epoch and admission checks still precede execution. Echo eligibility uses the original validated ancestry/session proof for direct prefix actions, otherwise the final session-bound scoped gate. Ordinary dirt must not revoke physical coverage after a proven rename. Folded debouncer Both events complete the maximal contiguous committed same-ID chain only after native lineage proof; pending folded chains use existing per-edge callbacks until full commit proof, with abort/expiry releasing repair evidence. Replacements and coverage gaps remain conservative. Verified disk settlement becomes durable `DiskCommitted` before the receipt; the reconciliation-owned worker projects affected roots afterward. Object batches are compensated all-or-nothing once started; bulk-mod chunks retain best-effort accounting. Parent confirmation is bound to filesystem evidence. Hash/key overlap is advisory, while physical destination collisions still reject without overwrite.
- **Toggle destination checks:** A request-scoped sibling-name index retains every folded-name candidate without a persistent cache. Toggle planning checks the actual destination, not prefix-equivalent logical siblings. Each apply/retry validates source ownership and uses atomic no-overwrite rename; only a failed rename needs a fresh collision census. Raced collisions follow the actual OS namespace, without promising virtual case-insensitive exclusion on case-sensitive filesystems.
- **Conflict Rename Recovery:** Conflict plans journal source filesystem identity. Staged conflict renames are siblings inside the game root; recovery validates that exact stage location and identity before rollback. Conflict, collection rollback, and mutation recovery use one non-overwriting filesystem rename primitive. Windows and Linux perform atomic destination exclusion; unsupported platforms fail closed.
- **Active Mod Conflict Review:** The scanner groups active conflicts by their canonical set of mod paths. A user may persist an ignored group per game in the additive `ignored_active_mod_conflict_groups` table; ignoring only suppresses review visibility and never changes a mod's enabled state. The frontend defaults to unresolved groups, can surface ignored groups for restoration, and sends paths rather than trusted keys so Rust canonicalizes and bounds every persistence request.
- **Collection Apply:** Preset application diffs only active and target roots, loads rename targets and object rows by affected keys/IDs, journals expected filesystem identities, and runs trusted root-scoped projection after the rename batch. Interactive apply follows task/DB finalization with a terminal disk-authority pass under its mutation lease; a post-commit reconcile failure returns a sync warning instead of inviting an unsafe rename retry. Runtime generations are reserved synchronously from known old/new rewrite roots before lease release; optional leaf derivation/INI work runs in the existing worker, not under the storage lease. Current-state capture holds both game and operation leases after its projection barrier. Safe Mode shares that barrier before reading or deciding the library is empty, releases the snapshot lease, then uses normal scoped apply.
- **Runtime Synchronization:** Filesystem and DB commit are synchronous authority boundaries; KeyViewer publication/reload is reconstructible and runs through a per-game, latest-wins async queue. Leaf mutations enqueue stable mod IDs, parent mutations enqueue compact root scopes, and superseded generations stop at bounded checkpoints while leaving a coherent warm base for the merged successor request. Warm composition caches retain all enabled contributions for a bounded number of games, and unchanged per-mod harvests are shared through `Arc` values instead of deep-cloned. `runtime_sync:status` reports queued/running/succeeded/manual-reload/failed generations. Runtime preflight and per-mod INI harvests are fingerprint-cached in memory, while the generated artifact and manifest remain atomically published on disk. Observer-ready mods without switcher keys still receive a KeyViewer panel with an empty-state message; mods without a detectable observer remain excluded.
- **Paged Explorer:** `get_workspace_structure` returns bounded navigation context and registered object metadata only. Folder search/sort/filter runs through cursor-paged `get_workspace_explorer_page` responses (maximum 200 items); one bounded-LRU server snapshot owns the sorted candidate set and opaque listing revision for a cursor session so later pages and bulk selection do not rescan or silently absorb newly appeared folders. Expired revisions return `ExplorerSnapshotExpired`, allowing the frontend to restart the exact query and discard stale selection. Bulk “all matching” selection stays symbolic in React and is resolved against its immutable snapshot with explicit exclusions and the existing mutation safety limit.
- **Mod Ingestion:** `Ingestion` receives an archive -> validates space and analyzes/extracts it through the `compress-tools` secure iterator into staging (including entry path/type validation, byte and ratio quotas, nested archives, password, progress, and cancellation) -> hands off to `Matching` for metadata -> hands off to `Mutation` to commit to disk -> `Workspace` refreshes. Staging is the sole archive extraction pipeline; it retains source archives and routes publication through Mutation. Ordinary per-item validation/hash failures persist retryable Failed/Partial state. Folder-pack discovery/grouping and 64 KiB copying poll the same cancellation token, preserve file permissions/modified time and reject linked entries. Per-batch extraction state serializes analysis and makes cancellation wait for extraction to stop before staging cleanup. Physical path/mount matching applies Windows disk-space quotas to existing staging directories and missing descendants alike.
- **Frontend Filesystem Boundary:** React has no `plugin-fs` capability. User-selected theme import/export dialogs and all resulting reads/writes are owned by validated Rust commands.
- **Mutation Recovery:** Durable operations record filesystem steps before mutation. Disk-first toggles persist an acknowledged `DiskCommitted` before deferred projection; other compensated transactions retain their DB-finalization boundary. Recovery never rolls back an acknowledged disk commit. Immutable journal plans and compact atomic `.active` progress records remain versioned, revisioned, checksummed, and operation-bound. Format 4 reads checksummed formats 1/2/3 and requires a format-4-compatible reader for recovery; downgrades must not discard journals or receipt evidence. Terminal snapshots precede active-state cleanup. Startup validates configured root/participant identities and path containment, compensates only unambiguous pre-commit states, and preserves current-root committed work for projection. Foreign-root/ambiguous acknowledged commits remain nonterminal with `NeedsRepair` projection status and durable evidence; normal projection skips them. Unrecoverable pre-commit work uses `FailedNeedsRepair`.
- **Durable Mutation Recovery:** Conflict, organizer, import, delete/rename and collection writers plan under the shared lease, preserve source ownership through apply/compensation, and never overwrite a raced destination. Organizer retains the original destination ancestry before waits and creates missing components through pinned-parent, no-overwrite publication rather than adopting newly appeared directories. Metadata saved successfully on disk is not rolled back when projection fails. Acknowledged commits belonging to a replaced root remain durable repair work, never rollback candidates.
- **Collection completion receipts:** The additive `mutation_projection_receipts` table binds an operation UUID to its game and original root epoch in the same SQLite transaction that finalizes collection/task state. `collection-apply-receipted` recovery requires the startup projection pool, validates the root and participants, then uses only an exact receipt match as commit evidence. Legacy `collection-apply` operations without durable completion proof remain manual repair, even when their root is known. Matching receipts are cleaned only after durable terminal completion; mismatches and repair evidence remain intact. A retained orphan receipt cannot authorize another operation.
- **Collection mutation ownership:** Capture the original Mods root before asynchronous preparation. Runtime and object attempts publish only the identity-checked source handle into its originally pinned parent; retries and compensation retain that namespace. After intentional object renames, rebase destination participants and hold verified post-mutation ancestry/leaf pins through trusted projection, including successful stale-spelling no-op participants, releasing them before compensation. Finalization pins and revalidates the original root through its receipt transaction. Do not hold mod-parent pins across a planned rename of that object itself.
- **Copied import ownership:** Same-volume import validates the planned source identity against a rename-capable handle and retains that handle and its original parent pin through publication. Cross-volume import holds those pins through copy and retires the original source with the same handle before releasing it for owned cleanup. Cross-volume publication returns the target's captured native proof; rollback only removes that owned target, never a later replacement. An interrupted copy whose ownership cannot be established from the durable source proof remains `FailedNeedsRepair` with payload/evidence retained; recovery does not guess or delete it.
